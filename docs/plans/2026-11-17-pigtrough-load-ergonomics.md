# pigtrough: loading the credentials (design question, for the operator)

Status: options and a recommendation; nothing built. This is the "`pigtrough
load` ergonomics" item parked by the coordinator.

## The problem

R3 (ruled 2026-11-17): the systemd user unit restarts `pigtrough serve`, and
every route comes back unloaded, answering `503 secret-unavailable`, until
the operator loads it. Today a load is, per route and by hand:

    piggy pass show <entry> | pigtrough load <route>

With several routes, after every restart, that is several commands and, for
each, a decrypt through piggy (the card, via the agent). The `secret` field
of each route in the route table already names the entry, so the operator
retypes what the file knows.

What must not change (R3): no unattended card use. A load happens only when
the operator starts it.

## Option A: a load-all helper, same trust

A command that, for every route of the table, runs the same pipeline the
operator runs by hand: `piggy pass show <secret> | pigtrough load <route>`,
one route after another, stopping at the first failure and printing only the
route name and ok/failed (never a value). Shapes: a script generated by the
home-manager module from `services.pigtrough.routes` (which knows the
`secret` names), or a `pigtrough load --all --routes FILE` that runs `piggy`
as a child. The secret still flows only through a pipe into `load`, as now.

- Trust: unchanged. The operator runs it; the card decrypts exactly when the
  operator asked (per piggy's own PIN and touch policy; whether one unlock
  covers every entry depends on piggy's PIN cache, which this session has not
  checked for these entries).
- Cost: small. The module-generated script needs the route table in nix
  (`routes`, not a hand-written `routesFile`); the `--all` flag would make
  `pigtrough` exec `piggy`, a runtime dependency it has not had.

## Option B: a oneshot unit the operator starts

A user unit, `pigtrough-load.service`, `Type=oneshot`, never enabled and not
`WantedBy` anything, whose `ExecStart` is Option A's helper. The operator
recovers from a restart with `systemctl --user start pigtrough-load`. The
journal records when it ran and whether it failed.

- Trust: as A: it only runs when started by hand. The unit must run in the
  operator's session environment for the PIN dialog (`SSH_ASKPASS`, the
  display); a user unit started from a shell inherits it, one started by
  `systemd` at boot would not, which is why it is not wanted by anything.
- Cost: A plus one unit and its eval test. It adds a name for what A is, not
  new power.

## Option C: the proxy fetches its own credentials

`serve` asks the piggy agent for each route's secret at start (and on every
restart), with no operator command. The agent would need a new extension to
release a named secret to the proxy, and a policy for who may ask.

- Trust: this is unattended card use whenever the agent already holds an
  unlocked PIN, which is what R3 ruled out; it also needs the policy layer
  (acts and stencils, #386) to say which process may read which entry, or any
  process of the user could ask for any secret.
- Cost: a new agent protocol surface and the policy work. Not for the pilot.

## Recommendation

A, delivered as the module-generated helper, with B as the way to run it.
Together they reduce recovery to one command and keep R3 intact. C waits for
the policy layer and a fresh operator ruling.

Two things to decide, neither a blocker:

1. Whether the helper may assume `services.pigtrough.routes` (the route table
   written in nix) or must also work from a hand-written `routesFile`. The
   first is simple; the second needs the helper to read the file at run time.
2. What the helper does when one route fails (stop at the first, as
   recommended, or continue and report). Stopping is safer for the PIN
   prompts: a wrong or locked card does not trigger a prompt per route.
