# `piggy card rotate-admin`: one verb for the management-key rotation

Date: 2026-11-19. Status: a design note, no code. Design owner: the FDR
0006 owner, who placed it under FDR 0006's card provisioning beside `card
init`'s management-key escrow (piggy#258), not a new FDR. Asked for by the
operator through the card coordinator after the circus card-day wrapper
(`mgmt-key-rotate`, a shell script over `piggy tool` and `piggy pass`)
reached the limit of what a shell can hold safely; circus#448 names the case
it cannot do at all, the LATER rotation. Nothing here is fleet-specific: no
host, card or sitting is named, and the verb must not know any.

## 1. Why a verb

The wrapper does the first rotation of a card's management key (factory
default to a key sealed in the store) in five steps, each a `piggy` call,
with the checks between them in bash. What bash does badly, piggy already
does well:

| The wrapper | piggy today |
|---|---|
| guesses whether the store entry exists three ways (`pass ls` full path, tree-shaped `ls`, a file under the store) | the store sealer resolves a pass name directly (`ManagementKeySealer::prepare`, `recover`) |
| pre-scans the `piggy-ids` file by regex and STOPs on a pigpen pointer document ("no resolver") | `pass insert` already resolves a pigpen pointer at encrypt time (`pigpen_pointer::resolve_piggy_ids_path`, RFC 0009 §3.2, RFC 0010); `prepare` returns the resolved recipients |
| `openssl rand -hex 24` into a shell variable, then through two pipes | a `piggy-guard` allocation (FDR 0006 guarded memory), never a string, never in argv or env |
| probes `piggy tool nope` for the usage banner to learn whether `auth-test` exists | the verb is the version |
| `CARD_DAY_ROTATE_RESUME=1` for the one crash case it knows | the state on the card and in the store says where to resume (§4) |
| cannot do a later rotation (circus#448) | `-K @store:<pending>` and `set-admin -` exist for exactly that (piggy(1), piggy#396) |
| a typed word read with `read -r -p` | the card `Frontend` (RFC 0006), so `card init`'s tty and `manage --jsonrpc` frontends both carry it |

The verb removes the shell's heuristics and keeps its discipline: every
gate fails closed before the card is written, the one write is behind a
typed word, the result is proven both ways, and the key is never typed,
printed or passed on a command line.

## 2. The surface

```
piggy card rotate-admin [--guid GUID] [--entry NAME] [--frontend tty|jsonrpc --socket PATH]
```

- `--guid`: the card, as `card init`'s selector takes it; exactly one card
  must match. There is no default to "the only card": the operator names the
  card the key is for, so a sealed key can never land under another card's
  path.
- `--entry`: the store entry, default `piv/<GUID>/management-key`
  (`card::seal::default_pass_name`, the entry `card init` seals and `-K
  @store` reads). The pending entry of a later rotation is `<entry>.pending`.
- No `--new-key`, no `--current-key`: the new key is always generated by the
  verb; the current key is always the factory default or the sealed entry,
  decided by the state (§4). A management key never crosses argv.
- Output: TAP-14 on stdout, one point per gate and step, as `piggy health`
  prints (so a wrapper's verify reads a plan and `ok`/`not ok` lines, not a
  magic last line); the recipients and the state are TAP diagnostics;
  nothing secret is ever in them.

## 3. The two rotations, one sequence

Letters as the wrapper's, so the operator's checklist carries over.

First rotation (no entry; the card is on the factory default key):

- **a. preflight, no PIN, nothing written.** The store is writable; the
  entry does not exist; the recipients the entry would be sealed to are
  resolved through the sealer (a pigpen pointer is resolved here, so the
  RESOLVED set is what the operator sees), checked by
  `check_escrow_recipients` (never empty, never only a key this card is about
  to lose); the card is not in PIN-protected management-key mode (below);
  the factory key authenticates (`auth-test`); the resolved recipients are
  shown and the operator types the word `seal` (§5). Anything short of that
  is a stop with nothing changed.

  The PIN-protected gate: a YubiKey can keep its management key under the
  PIN, in the Printed Information object (`5FC109`; piggy#198 is the mode in
  piggy, not built). Such a card is keyed by a key the store never held, so
  sealing a key to the store and calling it the card's would be false. The
  verb reads the Printed Information object's management-key field when the
  card lets it (the read may be PIN-gated: one PIN, through the frontend) and
  refuses a card that keeps the key there (exit 5, naming the mode and
  piggy#198), before the state table is consulted; and the state table's
  "none authenticates" row says the same before it says "factory reset".
  fibby does not model the mode; a `MockCard` row covers the gate.
- **b. generate.** 24 random bytes in guarded memory.
- **c. seal and read back.** `KeyEscrow::seal`, then `recover` (one 9D PIN,
  through the askpass safety net); compared in guarded memory. A mismatch
  rolls the seal back and stops; the card is untouched.
- **d. rotate.** `set_management_key_3des(new)` authenticated with the
  factory key. A refusal leaves the card on the factory key and the entry
  sealed and proven: the state §4 resumes from.
- **e. prove.** The new key authenticates (the read-back already proved the
  store holds what memory holds, so authenticating with memory proves the
  store's copy; no second PIN); the factory key no longer does; `commit`.

Later rotation (the entry exists and authenticates; circus#448):

- **a.** as above, plus: the current key is read from the entry (one 9D
  PIN) and must authenticate; the pending entry does not exist.
- **b., c.** as above, sealed at `<entry>.pending` and read back.
- **d.** `set-admin` from the entry's key to the pending key.
- **e.** the pending key authenticates, the entry's key no longer does; then
  the pending entry is promoted over the entry: one `rename(2)` of the
  pending entry's ebox over the entry's ebox, within one directory, which
  POSIX makes atomic (the entry is either the old key or the new, never
  absent or half-written), then one store commit. A crash between the
  rename and the commit leaves only an uncommitted tree, which the next run
  commits before anything else ("finish the last promotion": the state
  table reads the tree, not the index). The superseded key is gone from the
  tree: a key the card no longer takes is not kept where a tool could pick
  it. It stays in the store's git history, sealed to the same recipients,
  which is harmless once the card has refused it; the verb does not rewrite
  history and says so. Until e completes the old entry is untouched, so a
  crash anywhere before it leaves the old key in the store and the new one,
  if it reached the card, in the pending entry (§4).

Steps d and e run under one `PinSession`, which is one PC/SC transaction
(`begin_pin_session` takes it; `authenticate_admin` and
`set_management_key_3des` are its methods), so the agent's own use of the
card cannot interleave between the rotation and its proof; a second client
waits, as fibby's loopback test shows with `SCARD_E_SHARING_VIOLATION`.

The irreversible window the wrapper's step c exists to close is the same
here and is closed the same way: the card is written only with a key that
has been read back from the store.

## 4. State, not flags, decides where to start

The verb reads three facts before any PIN: does the entry exist, does the
pending entry exist, and which key authenticates (factory, entry, pending:
`auth-test` costs nothing and no PIN; a store read costs one 9D PIN and is
done only when the state needs it). Every combination is a row:

| entry | pending | authenticates | meaning | action |
|---|---|---|---|---|
| no | no | factory | fresh card | first rotation, a to e |
| yes | no | factory | first rotation died between c and d | read the entry back, d, e |
| yes | no | entry | steady state | later rotation, a to e |
| yes | yes | entry | later rotation died between c and d | read the pending entry back, d, e; a pending entry that will not read back (partial, unreadable, not 48 hex digits) is deleted and the later rotation starts again from a: the entry authenticates, so the pending key never reached the card, and a corrupt pending entry must not hold the card hostage |
| yes | yes | pending | later rotation died before promotion | e's promotion only |
| no | yes | pending | not a state the promotion's rename produces, but one the verb can finish | e's promotion only: rename the pending entry to the entry, commit |
| no | no | none of them | the card is on an unknown key and nothing is sealed | stop (§6, exit 6) after the PIN-protected gate has spoken: the recovery is a factory reset, which this verb never does |
| yes | any | none of them | a sealed key the card does not take | stop (§6), same gate first |
| no | yes | factory or entry-less | a pending entry whose key the card does not take, with no entry | stop: inspect by hand (the pending entry is not deleted: nothing authenticates to prove it dead) |
| yes | yes | factory | a card reset under a sealed store | stop: inspect by hand |

A row that stops names itself and what to look at; it never guesses, and
no row stops on a state the verb's own steps can produce. The wrapper's
`CARD_DAY_ROTATE_RESUME=1` becomes the second row.

## 5. The typed word is the frontend's

RFC 0006's `confirm` is yes/no. The rotation's confirmation is a typed word
(`seal`), because a stray Enter must not seal a key to a recipient set the
operator did not read. Proposal: `ConfirmRequest` gains an optional `word`
(RFC 0006 §2.4 amendment): when set, the tty frontend prints the message,
then `Type 'seal' to continue (anything else stops):`, and answers `true`
only for that exact word; the JSON-RPC frontend receives the word in the
request and answers `confirmed` as it sees fit (a UI may render a button
that types it). The engine treats a declined or cancelled confirm as "the
operator said no" (exit 4), distinct from any card refusal (§6). A word is
not a secret and is never asked through `request_secret`. As for every
other confirm, a JSON-RPC frontend that answers `confirmed` without a human
is that frontend's trust, which RFC 0006 should say at the amendment.

The recipients are shown through `progress` lines (step `recipients`, one
per key, as the store spells them) before the confirm, so the JSON-RPC
frontend can list them the same way the tty does.

## 6. Exits

One table, as the `ca` verbs have one:

| exit | meaning |
|---|---|
| 0 | done and proven |
| 1 | stopped with nothing changed, for a reason the TAP names (store not writable, a state row that stops short of the irreversible one, a read-back mismatch after rollback) |
| 2 | usage |
| 3 | the store cannot seal: no store, no recipients, only the doomed recipient, a pointer that does not resolve |
| 4 | the operator declined: the word was not typed, or a PIN prompt was cancelled; nothing changed (or, after d, nothing further changed and the state row says how to resume) |
| 5 | the card refused, or is not a card this verb manages: no card or more than one, the current key does not authenticate, `set-admin` refused with the card still on the current key, a card in PIN-protected management-key mode (§3's gate) |
| 6 | the irreversible state: `set-admin` was accepted and neither the new nor the old key authenticates, or the state table's "none of them" row on a card the PIN-protected gate has cleared. The TAP says, in words, that only a factory reset remains and that this verb will not do it |

4 and 5 are the two typed errors the design owner asked for: a cancelled
PIN prompt is never reported as an authentication failure.

## 7. What stays outside piggy

The choice of host, card and store for a sitting; run-step and terminal
discipline; publishing the store afterwards (`pass git push` is piggy's
verb, the decision is not); store backups; the factory-reset recovery,
which stays a human act with the checklist's words; and the checklist
itself. The circus wrapper becomes one call of the verb plus those.

## 8. Where it lives, what it reuses

`crates/piggy/src/card/rotate_cmd.rs` beside `init_cmd.rs` and
`add_key_cmd.rs`; the engine half (`card/engine.rs`) gains `rotate_admin`
over the same seams `card init` uses: `ProvisionCard` (auth with a
management key, `set_management_key_3des`), `KeyEscrow` (`seal`,
`rollback`, `commit`) and `ManagementKeySealer::recover`, the `Frontend`
(`confirm` with a word, `progress`, `request_secret` for the 9D PIN through
the store read), `check_escrow_recipients`, `piggy-guard` for the key.
Nothing of `cmd/tool` is called: `auth-test`, `set-admin -` and `-K @store`
stay the hand tools; the verb is their sequence with the state and the
proofs. piggy(1) gets the verb; piggy-testing(7) the lane.

## 9. Tests

Unit, over `MockCard` and `MockEscrow` as `card init`'s tests: every row of
§4's table reaches its action or its stop, the corrupt-pending rule deletes
and restarts, the uncommitted promotion is committed first; the
PIN-protected gate refuses a mock card that keeps its key in the Printed
Information object (exit 5, before any seal); the read-back mismatch rolls
back and leaves the card untouched; a refused `set-admin` leaves the entry and
reports the resume row; the "none authenticates" state is exit 6 with the
recovery words; the typed word's absence is exit 4 before any seal; a
cancelled PIN is exit 4, an authentication failure exit 5; the key never
appears in any TAP line or progress message (asserted on the mock
frontend's transcript).

A fibby lane, `piggy_card_rotate_admin_fibby.bats` (fibby takes `set-admin`
and `auth-test`: the tool-admin lanes), one row per stop as the design owner
asked: a first rotation end to end (the store's piggy-ids naming fibby's 9D,
as the tool-admin-store lane does); a later rotation end to end (pending
sealed, promoted, the old key gone); resume from a sealed-but-not-rotated
entry; a cancelled word (nothing sealed, nothing written); a cancelled 9D
PIN at the read-back (exit 4, the seal rolled back) versus a current key
that does not authenticate (exit 5); `set-admin` refused with the card
still on the current key; the irreversible state made by hand (`piggy tool
set-admin` to a third key behind the verb's back, then the verb) is exit 6;
a pigpen-pointer `piggy-ids` with a stub `pigpen-resolver-<kind>` on PATH
seals to the resolved set and shows it under the word.

## 10. Cost, guessed

One worker, 1.5 to 2 days: half for the engine half and the verb over the
seams above, half for the fibby lane and its rows, half for piggy(1),
piggy-testing(7), the RFC 0006 §2.4 amendment and the FDR 0006 paragraph,
plus a design-owner read. Not measured; nothing of it is built.

## 11. Decided with the design owner (2026-11-19)

1. The pending entry is `<entry>.pending`, one path. Its ebox,
   `management-key.pending.ebox`, is one more ebox under the card's
   directory: the re-encryption walk behind `recipients sync` and the rest
   (`collect_eboxes`, every `*.ebox`) re-encrypts it like any other, and
   nothing in piggy matches on the management-key name except
   `default_pass_name` (exact) and `-K @store[:name]` (exact), so the name
   needs no rule.
2. The superseded key is removed from the tree at promotion, not kept under
   a dated name; it remains in git history, sealed, harmless once the card
   refuses it; no history rewrite (§3 e).
3. The typed word is `ConfirmRequest.word`, an RFC 0006 §2.4 amendment; a
   word is never asked as a secret (§5).
4. `rotate-admin` runs with `--frontend jsonrpc` from `piggy manage` (RFC
   0007) as well; nothing in the design prevents it.

Still open for the operator: nothing that blocks the code; the exit
numbers (§6) are the only table the circus wrapper will script against.
