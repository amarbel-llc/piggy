# RFC 0011 §7.3 — identifier conformance-vector corpus
#
# Scope: the PURPOSE SLOT of a markl ID (RFC 0011 §2.1's `purpose`
# production) — not the digest slot, not the checksum, not the registry.
#
# Why this file exists (RFC 0011 §7.4, linenisgreat/madder#273 ruling
# 13): piggy owns "what a markl purpose may contain" and trellis owns
# "what a trellis identifier may contain". Those are deliberately
# separate definitions, so they can drift apart silently. The mitigation
# is DETECTION, not coupling: piggy publishes this corpus, downstream
# grammars run the SAME lines against their own identifier production,
# and any verdict mismatch not recorded in §7.4's divergence register
# fails a gate the moment it appears.
#
# FORMAT
#
#   Blank lines and lines beginning with `#` are ignored.
#   Every other line is exactly:
#
#       <verdict> <TAB> <slot>
#
#   <slot> is the exact bytes of the purpose slot as they appear in a
#   markl ID, INCLUDING the quote characters when the slot is quoted.
#   It runs to end-of-line; no vector ends in whitespace, and no vector
#   contains a literal tab.
#
# VERDICTS
#
#   parse          A well-formed purpose under §2.1, and valid.
#   reject         Not well-formed under §2.1. A conformant grammar
#                  MUST fail to parse it.
#   parse-invalid  Well-formed under §2.1 — a conformant grammar MUST
#                  parse it — but refused by a decoder at validation
#                  time (§2.2, §2.3). A consumer testing only a GRAMMAR
#                  treats this exactly like `parse`; a consumer testing
#                  a full decoder expects the parse to succeed and the
#                  validation to fail.
#
#   The third verdict exists because grammar-validity and
#   decoder-validity are genuinely different questions here, and
#   collapsing them would make this corpus unrunnable against a bare
#   grammar — which is its whole purpose.
#
# In piggy this corpus is executed against go/internal/bravo/markl/
# marklid.peg by TestIdentifierVectors (go/internal/charlie/
# markl_registrations/identifier_vectors_test.go), via
# `just test-grammar-vectors`.

# ---- `@`: barred bare, carried quoted (§2.2) -----------------------
#
# A bare `@` cannot appear: it is outside the §2.1 inclusion set, and it
# is markl's own purpose/digest join, so the first `@` in an unquoted
# slot ends the slot rather than becoming content.
reject	a@b
reject	@
reject	a@

# Quoted, `@` is legal content and the slot carries it (piggy#227).
# Quoting is an escape mechanism, and one that could not carry the rune
# most in need of escaping would not be doing its job. §2.2 formerly
# banned `@` "under any circumstance, quoted or not"; that ban was a
# pre-narrowing artifact -- once the bare charset became an inclusion
# set, `@` was already impossible unquoted, so the ban's only remaining
# effect was to forbid the one spelling that resolves the ambiguity.
#
# Consumers MUST locate the join with a quote-aware scan, not the first
# `@`: in `"a@b"@blake2b256-...` the join is the SECOND one. This is the
# single most likely place for a downstream implementation to diverge,
# which is why all three spellings are pinned here.
#
# 0014-trellis.peg's MarklTerm comment already said exactly this; the
# two specs now agree.
parse	"a@b"
parse	'a@b'
parse	"@"
parse	"a@b@c"
parse	"@leading"
parse	"trailing@"
